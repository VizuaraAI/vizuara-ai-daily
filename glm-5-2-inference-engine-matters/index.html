01

The model — 744B parameters, ~40B active

Mixture-of-Experts sounds exotic until you see it from the compute side: instead of running every neuron in the network for every token, an MoE model keeps most of its parameters idle and activates only a fraction of them per forward pass. GLM-5.2 has 744 billion parameters spread across its expert layers, but only roughly 40 billion are active when it processes any given token. That is the number that matters for latency: it is what actually sits on the GPU doing work.

The practical consequence is that a 744B model behaves a lot more like a ~40B model in terms of arithmetic intensity. You still need to store all 744B weights somewhere — in our case, 744 GB for the FP8 build — but the per-token compute cost is that of a 40B dense model. This is the bargain MoE trades: more memory, less FLOPs per token, and meaningfully different scaling behaviour once you start batching requests together.

GLM-5.2 was 13 days old when we ran these benchmarks, released by Zhipu AI on June 13, 2026. It is a reasoning model — it streams a thinking chain before its answer — and Zhipu ships it natively in FP8 format, not BF16. The full-precision BF16 version would require approximately 1.49 TB of GPU memory, which simply doesn't fit a single 8-GPU node. FP8 at 744 GB is the correct reference point, not a compromise.

02

Two "8-bit" builds, one gap you didn't see coming

Before the results, it's worth being precise about what "8-bit" means in each case — because the same number of bits can mean completely different things once a model is actually running on hardware.

FP8 is a floating-point format. The NVIDIA H200 GPU's tensor cores speak FP8 natively — there is dedicated silicon on the chip, the DeepGEMM kernel, that can multiply FP8 matrices at full hardware throughput without any conversion step. When vLLM serves GLM-5.2-FP8, every matrix multiply in the model's attention and MLP layers runs directly on those tensor cores. The weights sit in FP8, the activations run in FP8, and the hardware is doing exactly what it was designed for.

Q8_0 is a different beast. This is the llama.cpp quantization format — the weights are stored as 8-bit integers, but Q8_0 integers are not something Hopper's tensor cores understand natively. When llama.cpp runs a matrix multiply, it first has to dequantize the Q8 weights back to a higher-precision format the hardware can compute with, do the multiply, then move on. That dequantization step is not free. It is pure overhead on every forward pass, for every layer, for every token in every request.

FP8: weights → tensor cores directly  |  Q8_0: weights → dequantize → BF16 → tensor cores

Both configs start with 8 bits per weight in memory. The difference is not how much memory they use — it's whether the arithmetic ever has to stop and translate. FP8 never does. Q8_0 always does. Add continuous batching, paged key-value memory, and CUDA graph capture to the FP8 path (via vLLM) versus the more conservative serving approach of llama.cpp, and you have two systems that share a description — "8-bit" — but very little else.

03

Throughput — one engine scales, the other doesn't

At a single concurrent request, the two configs feel roughly comparable. FP8 delivers 56 tokens per second system-wide; Q8 delivers 36. A 1.6× edge for FP8, which is meaningful but not shocking. You might conclude: "8-bit is 8-bit, the gap is modest, and the cheaper setup is close enough."

Then you add concurrency. At 8 simultaneous requests, FP8 is at 330 tok/s and Q8 is at 80. At 32, FP8 is at 779 and Q8 at 123. At 64 concurrent requests — the kind of load that represents a real deployment serving actual users — FP8 reaches 1694 tokens per second. Q8 plateaus at 186. That is a 9.1× gap, and it didn't exist at low load. It emerged as batching revealed what each engine can actually do.

What drives the FP8 divergence is vLLM's continuous batching. Instead of waiting for a request to finish before starting the next one, vLLM interleaves generation steps across requests — every decode iteration can include tokens from dozens of in-flight requests simultaneously. Paged key-value memory eliminates wasted KV cache allocations. CUDA graph capture turns the decode loop into a pre-compiled GPU operation with minimal Python overhead. Put it together and you have a system that gets more efficient as concurrency grows, not less.

The Q4 run (UD-Q4_K_M, ~400 GB) never completed — loading 744 GB over Modal's 9P network storage repeatedly stalled; one Q8 load alone took 84 minutes. The code was correct; Q8 ran end-to-end on the same path. It's an infrastructure throughput issue, not a model issue.
04

Latency — flat versus catastrophic

Throughput tells you how much work a system can do. Inter-token latency tells you how the system feels to a user. They can diverge in ways that matter: a system can have high throughput while individual users experience long waits between tokens, if the serving engine doesn't manage request isolation cleanly.

At a single stream, FP8 decodes at 17.6 ms/token. Q8 decodes at 27.4 ms/token. Both feel fine. FP8 has a 1.55× edge even at low load — Hopper's native FP8 tensor cores versus the dequantize-every-layer path — but neither is unusably slow. A 17 ms inter-token latency is imperceptible to a human reader.

Then you scale. At 8 concurrent users, FP8 is at 20.1 ms/token — barely changed. At 32 concurrent users, it's 20.9 ms/token. At 64 concurrent users, 22.5 ms/token. The FP8 line on the chart below is essentially flat. Q8's inter-token latency under the same load degrades 12-fold: from 27 ms to 332 ms at 64 concurrent users. That is the difference between streaming text that reads naturally and a system where each word appears after a third of a second of silence.

When you deploy an open model, the inference stack you choose can matter more than the precision you quantize to.

The reason FP8 stays flat is vLLM's continuous batching. The serving engine runs a decode loop where each iteration processes one generation step for every active request simultaneously. The per-token cost doesn't multiply with concurrency — it amortizes. More requests in flight means more useful work per GPU clock cycle, not more overhead per user. The throughput grows; the per-token latency barely budges.

06

What the data says

Four patterns jump out clearly from the numbers. Each one is a concrete, actionable lesson about what matters when you move from "which quantization format should I use?" to "what is my system actually going to do at load?"

9.1×higher throughput for FP8 at 64-way concurrency (1694 vs 186 tok/s)
22.5msFP8 inter-token latency under full load — essentially flat from single stream
12×Q8 inter-token latency degrades under load (27 to 332 ms)

Fewer bits does not mean faster

At a single stream, FP8 decodes at 17.6 ms/token vs Q8's 27.4 — a 1.55× edge, despite both being 8-bit. FP8 maps straight onto Hopper's dedicated FP8 tensor cores via DeepGEMM. llama.cpp dequantizes Q8 to BF16 for every matrix multiply. Same bit count on disk; different arithmetic at runtime.

Batching is the whole game

FP8 inter-token latency barely moves (17.6 to 22.5 ms) as concurrency rises 64×. Q8 collapses 12×. vLLM's continuous batching + paged KV memory + CUDA-graph decode keep per-token cost flat under load. llama.cpp processes requests more sequentially, so each new user multiplies the per-token cost.

Throughput diverges 9×

FP8 scales to 1694 tok/s at 64-way load; Q8 plateaus near 186. Almost all of this gap is the engine, not the quantization. If you ran Q8 through vLLM with native hardware support, you would see a very different curve. The gap is a property of the full stack — format plus engine together — not the format alone.

Tails reveal queueing

p99 TTFT climbs to ~10–12 seconds at c=32 for both configs as requests wait for a decode slot. The median looks fine; the 99th percentile tells the truth about what occasional users experience. Latency SLOs should be specified and measured at the tail, not the median. If you're debugging user complaints, check p99 first.

07

Field notes — what it took to serve a 13-day-old model

Running a model that had been publicly available for 13 days before we benchmarked it meant working through integration issues that older, more battle-tested models don't have. These are the practical notes — the kind of things that cost hours to debug and take ten seconds to read.

  • 1 Current Transformers required. vllm==0.23.0 requires transformers≥5.9. Older builds reject the glm_moe_dsa architecture silently or with unhelpful errors. Pin both versions explicitly.
  • 2 Sparse attention needs DeepGEMM. GLM-5.2's DSA / "IndexShare" sparse attention mechanism hard-requires DeepGEMM — meaning a full CUDA toolkit must be available at runtime, not just at build time. A slim Docker image fails with: Sparse Attention Indexer requires DeepGEMM. Include the full toolkit in your container.
  • 3 llama.cpp needs --no-mmap off network storage. Default mmap over Modal's 9P network volume stalls on the 744 GB sequential read. Pass --no-mmap to force sequential loading into RAM. Still slow: one Q8 load took 84 minutes.
  • 4 GLM-5.2 is a reasoning model. llama.cpp streams thinking tokens as reasoning_content, not content — the two fields are separate in the response structure. A benchmark client that only counts content tokens will read zero output. Count both fields or your throughput numbers will be zero.
  • 5 Cold start is long. FP8 on 8×H200 takes approximately 10 minutes to load weights, followed by ~22 minutes of torch.compile and CUDA graph capture before the first token can be served. Budget for this in Modal timeout settings and cost calculations.
Caveats about what this compares: This is engine + quantization together, not quantization alone. FP8/vLLM vs Q8/llama.cpp differ in both the numerical format and the entire serving stack — almost all of the ~9× throughput gap is the engine. The clean quant-only comparison is Q8 vs Q4 within llama.cpp, which we could not complete due to infrastructure constraints. Speculative decoding (GLM-5.2 ships an MTP layer) was off for both runs — enabling EAGLE-style spec-decode is a natural and likely large next lever. No accuracy evaluation: these are latency and throughput only.
08

Why this matters

The open-weight inference landscape is developing a new common assumption: that once you choose a model and pick your quantization level, the hard decisions are made. The bits are the budget. A smaller bit-count is a faster, cheaper model. But the GLM-5.2 numbers tell a different story.

Two configs at the same bit-width, 744 GB of weights each, running on the same cluster of 8 H200s — and they deliver 9× different throughput at scale. The weight format alone didn't do that. The dequantize-to-compute penalty didn't do 9× alone either. The gap is the product of four things layered together: the arithmetic path (native FP8 vs dequantize), the batching strategy (continuous vs sequential), the memory management (paged KV vs flat allocation), and the decode optimization (CUDA graphs vs interpreted Python loop). Those four things are almost entirely determined by the serving engine you choose, not the precision you quantize to.

The practical lesson for anyone deploying open models at scale: measure the full stack, not just the model card. The numbers on the spec sheet (parameter count, active parameters, context window) tell you what the model can do. The serving engine is what determines whether it can do it at the concurrency and latency your application requires. Run your own benchmarks at your target concurrency level. The single-stream numbers will lie to you.

GLM-5.2 itself is worth watching. At 40B effective active parameters, it's one of the most capable open-weight MoE models available, and Zhipu's choice to ship in native FP8 means the reference deployment is already tuned for the hardware that matters. The model is 13 days old as of this writing. The tooling will catch up. The benchmarks will improve. But the fundamental lesson — the engine matters more than the bits — will stay true for any model you run.
